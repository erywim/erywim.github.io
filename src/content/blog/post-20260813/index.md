# ▍名词解释

- Agent：（各个地方对其的定义不一致，这里选用Anthroptic对其的定义） LLM 动态指导自身流程和工具使用的系统，自己掌控完成任务的方式

- workflow：（各个地方对其的定义不一致，这里选用Anthroptic对其的定义）通过预定义代码路径来编排 LLM 和工具的系统

- 对话流（Prompt）中角色定义：

    - User：用户的提问（请求），需要模型针对性回答的问题内容

    - System：初始设定、全局规则。告诉模型“你是谁，该怎么回答”

    - Assistant：模型的**生成输出。（**如果作为输入则是**默认认为自己已经说过的话）**

- Memory：模型本身是无状态的，所以每次调用的时候将历史对话记录输入给模型称为 memory

- Prompt（SystemPrompt）：向模型提问时，预先给它定义角色，回答规范等信息，要求他做出行为的一堆指令

- Context：指的是模型在生成当前回复时所能“看到”的全部信息，通常包括：

    - 用户当前的 Prompt（System Prompt\+User Prompt）；

    - 之前的对话历史（包括模型输出，工具执行结果）；

    - 工具清单（MCP\&Function Calling）

    - ReAct Agent的Thought/Action/Observation等内容

    - 外部知识注入（如 RAG 检索结果）。

Context 是模型理解当前任务的依据。受模型最大上下文长度（max context length）限制。

- Lost in the middle：**当前的语言模型在长上下文中对信息的位置非常敏感，往往更关注开头和结尾的内容，而忽略中间部分的信息**。作者将这种现象称为“Lost in the Middle”（过程中迷失/遗忘初始目标）（https://arxiv\.org/abs/2307\.03172）

- Prompt Engineering 和 Context Engineering 的区别：Prompt Engineering 主要关注的是的Prompt如何去编写，如何指定模型应该怎么做出回应，而Context Engineering更关注的是模型在回答的时候能够看到什么内容

- RAG（Retrieval\-Augmented Generation，检索增强生成）：先检索外部知识库中的相关信息，再基于检索结果生成回答。解决模型知识有限、虚构幻觉和时效性不足的问题，让回答有据可依。

    - 向量化（Embedding）：Embedding 本质上是一种**分布式表示**，把离散的符号（字词、句子、文档等）映射成一个低维稠密向量，让“**语义/特征相近的对象在向量空间里距离也近**”，从而可以用向量距离、相似度来刻画它们的语义或功能关系。核心思想是“用一个向量里所有维度的激活模式一起表达一个概念”，而不是某个维度单独说了算

    - **单个维度没有稳定、直观的含义，但维度组合整体能表达语义和关系**。

        - **单个维度**：通常没有明确、人类可解释的语义（比如第 3 维不代表"情感"，第 128 维不代表"科技"），它是模型训练过程中自动学到的"隐式特征"，属于**潜空间**的抽象表示。

            - **潜空间**的定义：形式上，潜在空间被定义为抽象的多维空间，它编码外部观察事件的有意义的内部表示。在外部世界中相似的样本在潜在空间中彼此靠近。 比如狸花、金吉拉、银渐层这些词会彼此靠近

        - **整体维度组合，**才有语义意义。类比人脑神经元，单个神经元不表示具体概念，但一群神经元的激活模式就能编码"苹果"或"喜欢"。向量也是靠所有维度的数值组合，共同表达一个语义状态。

    - 就是因为embedding是分布式表示的，看的是高维空间的语义/特性，所以它是黑盒的，不可解释的。如果我们追求一定的确定性，那么可以使用BM25这类关键词检索的形式，但是这种形式又缺乏语义泛化能力，例如用五道口职业技术学院去检索清华大学就没方法命中。那么介于它们二者之间有像SPLADE这类方式

- 通常我们判断两个chunk是否一致是通过**余弦相似度**大小进行判断的。之所以这个值能代表他们之间是否相似，主要原因是现在主流的稠密向量，通常通过对比学习训练得到。很多损失函数它会对余弦相似度做直接的优化：语义相关的正样本要求夹角趋于0，语义无关的负样本要求夹角趋向于正交。模型为了压低损失，必须学会将语义相近的输入映射到空间中方向一致的向量上。也就是说，**夹角本身承载了模型所学到的全部语义判别逻辑**，它就是模型用来定义“像不像”的那个物理量。 **另一个好处是余弦相似度与向量的模长无关**，也就是说，即便文档再长，它只要表述的内容是和另一个文档（假设很短）是一致的，那么他们夹角就会很小，而欧氏距离则会收到长度的影响从而误判

    

- 首token：流式提问中，每一次向模型发送提问后，模型返回的第一个单字或词组。这是考量agent系统的重要指标之一

- Agent开发范式

    - 单Agent：一个独立的智能体独自完成任务，自主决策、调用工具、执行流程。所有逻辑和工具使用都在这一个Agent内部闭环，适合任务边界清晰、无需协作的场景。

    - Multi Agent：多个Agent分工协作完成复杂任务，每个Agent有特定角色和能力，通过通信机制（如消息传递、任务委派）协同工作。适合任务拆解后需要多专业配合、或需要竞争/验证机制的场景（如一个写代码、一个审代码、一个测试）。常见的架构是 `指挥官-工人` 架构。

        - Multi agent 核心解决的问题是随着长对话的进行上下文窗口的内容增多，由于注意力稀释机制导致的上下文腐烂，具体表现有指令漂移、上下文遗忘等。

    - ReAct\-Agent：这种属于一个agent构建范式，其核心是让模型在生成最终答案之前，通过交替进行“推理（Thought）→ 行动（Action）→ 观察（Observation）” 的多轮循环来动态获取信息、调用工具，最终形成基于充分信息的答案。

    - Reflection Agent：具备反思功能的Agent。当模型输出完答案之后，可以借助LLM使用预先定义好的提示词引导模型对于此次问答进行批判性反思，具体的维度可以自行定义。这种方式可以一定程度提高模型回答准确度，但是会提升成本和模型回答时间。

        - 这里需要注意：通常模型会对自己的工作给予高度肯定，所以尽可能引入其他agent去批判

    - Plan Execute Agent：这种架构主要分为两个部分，一是Planner规划器，将原始任务分解成具体的多个子任务或步骤，二是Executer执行器，基于规划器列出的任务或步骤\+可用的工具完成当前任务。PlanExecuteAgent的整个执行过程就是围绕着一个全局状态持续进行迭代与收敛的过程。相较于ReActAgent，这种方式的可解释性/效率都有显著的提升。但是实现难度也会增大，灵活性也会降低。一句话解释就是：**ReActAgent是边想边做，PlanExecuteAgent是想明白了再做**

- MCP：由Anthropic提出的开放标准协议，定义模型与外部数据源、工具之间的通信规范。类似"AI领域的USB\-C接口"，统一了模型获取上下文和调用工具的方式，无需为每个工具单独写适配代码。

- 模型蒸馏：大模型需要依托于庞大的数据集进行训练，参数量极大，训练/推理所需的算力成本也极高。而「模型蒸馏」的含义就是训练出一个小模型（也被称为「**学生模型」）**向预训练好的模型（也被称为**「老师模型」**）学习** ，**从而用更少的参数达到像大模型类似的能力。这种方式也被称为 **模型压缩**。

- Tool Calling \(Function Calling\)：让大语言模型具备调用外部工具、执行特定操作的能力。
这个机制允许模型：

    1. 根据用户请求，决定是否需要调用工具（以及调用哪个工具）。

    2. 以结构化格式（通常是JSON）输出调用工具所需的参数。

    3. 系统接收这个结构化调用，执行实际代码（如查询数据库、调用API、运行计算），并将结果返回给模型。

    4. 模型根据返回的结果，组织最终的回答给用户。

- Harness engineering：它是构建在模型之外的一整套运行时环境与控制系统，相当于给模型装上的“马鞍”或“操作系统”。它不改变模型，而是通过系统提示词编排、工具接口封装（MCP/API）、沙箱安全隔离、长短期记忆管理以及工作流调度等机制，将模型原本无状态、纯文本的推理能力，转化为可靠、可控、可持续运行的 Agent 行为，解决模型“如何安全落地并长久工作”的问题。换句通俗易懂的话来说：包裹在大模型外的一切（提示词、工具、沙箱环境、上下文管理）都属于Harness

    > **如果你不是模型本身，那你就属于 Harness**

- Skill：它是 Agent 专用的标准化行为包与知识模板，相当于告诉模型“这类任务具体该怎么做”的操作手册（SOP）。它通常由一段结构化的指令（如 SKILL\.md）及相关参考文档或脚本组成，通过按需加载机制复用 Tool Calling 协议动态注入上下文，指导模型在特定场景下如何思考、何时调用工具以及遵循何种规范，从而将通用模型的泛化能力转化为垂直领域的专业表现。

    - 它的实现机制本质上就是基于 Tool calling \+ 提示词 。用户定义了一系列的「skill\.md」文件，与tool定义一样必须要包含`name`与`description` ，然后将skill文件中的name与description作为提示词的内容传入模型，模型在运行过程中使用 `read_skill`的工具进行按需读取skill文件中的内容获取到相应能力以实现**渐进式加载**的效果。与传统的tool方式不同的是，skill的方式将tool的数量进行收拢，以一个 read\_skill 工具作为入口就能获取到许多skill
